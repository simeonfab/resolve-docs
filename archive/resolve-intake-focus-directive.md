# Resolve — Short-Term Focus: Intake Only

Status: active short-term directive
Supersedes: all "Later" and "Next" items in current-plan.md until exit criteria below are met

## The one thing that matters right now

Validate whether the **Existing Messy Project** route inside Resolve Intake actually works for someone who is not Simeon or his wife.

Nothing else. Not the Runtime Surface. Not ResolvePM Light. Not the intake router (Screen 0). Not new routes. Not repo convergence work. Those are written down and parked — they are not this quarter's work.

## What "Intake" means, scoped down

Resolve Intake, for now, is just: **the six-screen flow that takes messy project context and turns it into a clear understanding + path to execution.**

1. Bring Everything In
2. Your Project As I Understand It
3. Context Needed
4. Your Path To Execution
5. Potential Roadmap
6. Continue From Here

That's the whole product, for now. If an AI tool (Cursor, Codex, ChatGPT, Claude) is helping with Resolve work and suggests building anything outside these six screens, the answer is: not yet.

## What to actually do, in order

### Step 1 — Fix what the wife test already found
Before testing anyone else, close out the known, already-diagnosed problems:
- Unclear title/purpose on Screen 1
- Inconsistent terminology (idea / project / context / source — pick one vocabulary and use it everywhere)
- Simplify Screen 2 correction controls to Confirm / Edit / Reframe
- Clarify Screen 3's purpose in plain language
- Replace "add to backlog" language
- Remove redundant docs/repos question
- Add a free-entry option for desired outcome
- Add "or something else" on Screen 6

This is frontend copy/layout polish only. No backend, no new screens, no branching logic.

### Step 2 — Find 2–3 real external testers
Not family. Ideally people who fit the route: someone with an actual messy project (scattered across docs/chats/notes/a repo). Cold, no explanation from you beyond the prototype itself.

### Step 3 — Watch for three specific things
- Do they understand what each screen is for, without you explaining?
- Do they complete the flow to Screen 6?
- Do they want to do something with the output (share it, come back to it, act on it)?

### Step 4 — Decide, based on real evidence, not instinct
After 2–3 external tests, you'll have one of three outcomes:
- **It clicks** → now it's reasonable to design Screen 0 (the router) and consider a second route.
- **It's close but confused** → another polish pass on this same route, test again. Do not add scope.
- **It doesn't land** → that's real information too. Better to learn this now, on one route, than after building seven layers.

## Exit criteria — when you're allowed to move past Intake

Do not start on Runtime Surface, ResolvePM Light/Full integration, the router, or new routes until ALL of these are true:

- [ ] At least 2 external (non-family) testers have used the Existing Messy Project route
- [ ] They understood the purpose of each screen without your explanation
- [ ] They reached Screen 6 and could articulate what they'd do with the output
- [ ] The known usability issues from the wife test have been addressed and re-tested

## Standing instruction for any AI tool working on this

If asked to help with Resolve, ResolveOS, ResolvePM, or Resolve Intake work right now:

- Only frontend copy/layout changes to the six-screen Existing Messy Project prototype are in scope.
- Do not propose, design, or scaffold: the intake router, ResolveOS Runtime Surface, ResolvePM Light, new routes, backend/API work, accounts, persistence, or repo merges.
- If a good idea for a later layer comes up, note it as a backlog item — do not act on it now.
- If unsure whether something is in scope, the test is: "Is this one of the six screens, or does it make the six screens clearer?" If no, it's out of scope for now.
