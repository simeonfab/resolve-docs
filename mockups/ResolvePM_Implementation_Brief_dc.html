Read this first — global conventions

  • Two surfaces, one system. The intake flow (pre-auth) is a desktop-width web experience with a 4-step left stepper. The app (post-auth, "ResolvePM") is mobile-first for Alpha (390px), desktop to follow. Same tokens throughout.
  • Light Surface is the base. Dark Ink is reserved for one dominant moment per screen (win card, recommended-action card, welcome veil). Never a dark theme throughout.
  • App navigation is a fixed bottom tab bar — steady-state order Dashboard · Work · Roadmap · Team · Knowledge. During onboarding only Roadmap is unlocked (the rest are visible but locked) until the roadmap is confirmed. Settings is not a tab — it opens from the header profile avatar.
  • Global orchestrator = a floating pill (docked above the tab bar), on every tab once the app shell has revealed — not during the chrome-free build sequence. Prompt + suggestions are contextual to the current tab; it drives ask · find · navigate · capture · confirmed-create and opens into one sheet. It supersedes the old "Search workflows · Ctrl K" sidebar element.
  • Loaders narrate. Every processing wait shows a short checklist of what Resolve is doing (not a bare spinner). Loaders run once through in product.
  • First-run vs recurring. Grand/one-time moments (OS assembly, Team intros) play only on first visit; every later open is the subtle version.
  • Persistence. The Dashboard "win for today" and the confirmed Roadmap are stored, stable state — not recomputed on load. The win changes only when its task is completed or explicitly superseded; never show a "refresh" affordance.

Part A

Intake (pre-auth, desktop)

1 · Name entry

ResolvePM Onboarding.dc.html

Purpose. Capture the user's first name to personalise everything downstream.

Flow. First screen after landing → on submit, advances to the welcome/problem reveal.

Behaviour. Single field, autofocused. Enter submits. "Continue" stays disabled until a name is entered (no dead-end). Eyebrow is sentence case ("Let's get started").

2 · Welcome → problem (fused reveal)

ResolvePM Onboarding.dc.html

Purpose. The delight beat and the first real question on one screen.

Flow. "Hi [name]." reveals as the serif hero and holds; "Welcome to Resolve" gives way as the question and three paths animate in beneath the same headline.

Behaviour. Options: I have a messy project (live) · I have a new idea / I'm stuck (both "Coming soon", disabled). Selecting the live path advances to step 2. The top step counter is hidden during this moment — the sidebar stepper is the progress. Question is Inter so the screen keeps one serif element.

3 · Bring it in (step 2)

ResolvePM Bring It In.dc.html

Purpose. The context dump — messy notes, pastes, anything.

Behaviour. Large textarea is the hero (voice-input affordance in corner). Starter chips ("A rebrand that's stalled" etc.) prefill a scaffold to beat the blank page. Helper hierarchy: Try an example (primary) · paste-from-another-chat prompt (link) · Add material (disabled, Coming soon). "Build my path" is disabled until there's content.

4 · Reading loader → Confirm understanding (step 3)

ResolvePM Confirm Understanding.dc.html

Purpose. Show what Resolve extracted and let the user correct it before it drives everything.

Flow. "Reading your project…" loader (reading → separating decided/open → spotting gaps → shaping) → confirm screen.

Behaviour. Four understanding cards (project, what you want, where it is, biggest uncertainty), each individually editable (per-card pencil). "A couple of things Resolve still needs" = optional gap questions. "What Resolve is assuming" is challengeable inline ("Not quite?"). Forward action in footer builds the path.

5 · Weighing loader → Your next move (step 4)

ResolvePM Next Move.dc.html

Purpose. Deliver the single highest-leverage action + the shape of what follows.

Flow. "Weighing it up…" loader (weighing → checking against confirmed → sequencing → choosing first move) → next-move screen.

Behaviour. The dark "Do this first" card holds the one serif element (page title is Inter). "This week" item in the timeline is flagged active. Footer "Continue" leads to the celebration handoff.

Part B

Handoff & sign-up

6 · Final intake screen + bridge transition

ResolvePM Intake Transition.dc.html

Purpose. Turn "leaving intake" into an earned reward, then carry the moment into the app without a hard cut.

Flow. Trophy celebration + the recommended-action handoff card are on screen together. User taps Continue in Resolve → a ~1.6s bridge (no click): fog headline lifts → first move pins with an amber check → Resolve mark + context chips form ("setting up your workspace") → settles into the sign-up screen.

Behaviour. Single dominant amber CTA; "Not now" is a quiet link. Copy is benefit-led (first move + roadmap + full context carry across) — not "send session data".

7 · Sign-up / login (OTP)

ResolvePM Sign-in.dc.html

Purpose. Create the workspace via one-time code (not magic link).

Flow. Email entry ("Send code") → 6-digit code entry ("Verify and continue") → into the app build sequence.

Behaviour. Six individual digit boxes. Resend has a cooldown (respect the mailer rate limit) — link disabled with a countdown, re-enabled after. Wrong/expired code shows an inline error, no page reload. All copy says "code", never "link".

Part C

Post-auth build sequence (mobile, chrome-free)

A focused, full-screen sequence with no app chrome — this is the user "signing" their roadmap before the OS appears. A 3-segment progress bar threads it: Themes → To-do → Roadmap.

8 · Roadmap theme cards

ResolvePM Roadmap Cards.dc.html

Purpose. Confirm the strategic themes one at a time; make the roadmap visibly form.

Behaviour. One card per theme (3 total). "Yes, add to my roadmap" drops the theme into an "On your roadmap" list (check pop) and advances. "Not quite" opens an inline correction field — on save it swaps the wording and adds the corrected version (correction re-runs the theme-vs-task check server-side). No reject/remove path in Alpha — every theme ends on the roadmap, correction-only. End state hands to the to-do list.

9 · To-do list reveal

ResolvePM Todo List.dc.html

Purpose. Show the concrete first-week list generated from the roadmap.

Behaviour. Auto-plays: setup meta-steps ("Set up workspace", "Confirm your roadmap") check off and strike through, then the first real task surfaces as the dark "Up next" row, upcoming tasks below. Counter ("2 of 12 complete"). Headline copy is placeholder — confirm wording.

10 · Roadmap reveal

ResolvePM Roadmap Reveal.dc.html

Purpose. Present the plan as a Now / Next / Later grid, then open the door to the agents.

Behaviour. Reveals column by column (themes → Now, amber-emphasised → Next → Later), then drops in the Product Director to invite questions or additions before entering the app.

11 · OS assembly → Dashboard

ResolvePM OS Reveal.dc.html

Purpose. The grand, one-time reveal of the whole Resolve OS.

Behaviour. First run: dark "Welcome in, [name] / Your operating system is ready" beat → veil lifts → header drops in, bottom tab bar slides up, the four Dashboard cards populate in leverage order → settles on the Dashboard. Every later open: no dark beat; the shell's already there, content just settles in with a quick fade. Both land on the Dashboard.

Part D

The app (mobile shell, bottom tabs)

12 · Dashboard

ResolvePM Dashboard.dc.html

Purpose. Answer "what do I do next?" Four cards, fixed order.

Behaviour. Win for today dark full-width card, serif headline, entire card is the tap target — no button; routes contextually by action type (work item → opens it; agent-relevant → that role's chat). Blocked only external-input stalls. Schedule today's meetings + to-dos. Pointer a lighter nudge (roadmap). Tapping any card expands it in place — background dims, detail surfaces inline, no open/close buttons. The win content is stored/stable (see persistence).

13 · Roadmap tab

ResolvePM Roadmap Tab.dc.html

Behaviour. View toggle: By phase (Now/Next/Later stacked, Now emphasised) ↔ By theme (theme cards, each with its own Now/Next/Later rows). Product Director floating button pinned bottom-right (above the tab bar) — reachable from any scroll position.

14 · Work tab

ResolvePM Work Tab.dc.html

Purpose. The execution surface (distinct from Roadmap's plan). Week-progress bar up top; checkable rows.

Behaviour. Sections in order: Now (active, amber) · Waiting on (external-dependency stalls, "Waiting · Nd") · Captured inbox (Alpha empty — fed by the global input bar) · Upcoming from roadmap · Synced from tools (Alpha empty). Pre-populated from confirmed roadmap items — never starts blank.

15 · Team tab + agent chats

ResolvePM Team Tab.dc.html · ResolvePM Agent Chat.dc.html

Purpose. The AI agent roster: Product Director, Growth Lead, Tech Lead.

Behaviour. On first visit each lead introduces itself in plain English, contextualised to the project (staggered intro; static thereafter). Tapping a lead opens an individual chat (project-contextualised greeting + starter prompts; same pattern for all three). The Stand-up room lets the user address the group — only the relevant leads respond (not all three every time), each reply labelled with who's speaking.

16 · Knowledge base tab

ResolvePM Knowledge Base Tab.dc.html

Purpose. Read-only view of the intake handoff.

Behaviour. "Read-only · captured at intake" pill. Sections: project understanding (the four intake cards, no editing) · recommended action · full report (view/download PDF). Alpha scope: no search/ask, no decision tracking — Beta or later.

17 · Settings

ResolvePM Settings.dc.html

Flow. Opens from the header profile avatar (menu: Profile · Settings · Sign out) — no sixth tab.

Behaviour. Groups: Account · Workspace (project, plan) · Preferences (daily briefing, waiting-on reminders toggles) · Session. Reset onboarding flow lives in Session — it clears the current session and replays the intake from the start, but keeps the saved roadmap intact. Sign out below it.
